# PR AI Review Loop

After all code changes are pushed and all required CI checks pass, run these phases in order **before** enabling auto-merge on the PR. A required check that skips while the PR is a draft counts as passed here, but it has not run yet: it first runs once Phase E marks the PR ready. Phases B, C, and D each have their own configurable maximum number of rounds (`MAX_CODE_REVIEW_ITERATIONS`, `MAX_SECURITY_REVIEW_ITERATIONS`, `MAX_COVERAGE_ITERATIONS` respectively). Phase A uses its own, separate budget (see below).

Round caps: use these values unless the run sets its own (the orchestrator passes them in the prompt), and never invent a lower one, because a cap that is too low blocks a PR that a few more rounds would have finished:

- `MAX_SIMPLIFY_ITERATIONS`: 10
- `SIMPLIFY_THRASH_LIMIT`: 3
- `MAX_CODE_REVIEW_ITERATIONS`: 15
- `MAX_SECURITY_REVIEW_ITERATIONS`: 15
- `MAX_COVERAGE_ITERATIONS`: 6

The Orchestrator runs each review and judges convergence and thrash, but never implements directly: it hands every file change, commit and push to the fix route below.

## The Fix Route

Every fix the loop needs runs: Code Fixer (or Code Writer, when the step names it) → Code Tester → Changelog (correction) → Committer → PR Submitter → CI Monitor. It drops the Pre-Work Baseline Check, because that check already ran when work on the PR began, the Committer before Code Reviewer, because the single Committer after Changelog (correction) commits the change, and Code Reviewer, because the loop's next phase or round reviews the change anyway. Changelog (correction) runs against the resulting diff, and Committer commits `CHANGELOG.md` as a separate commit whenever Changelog produced a correction.

Each Code Writer or Code Fixer task carries exactly one change (one finding, one construct, or one approved request), and that change goes through Code Tester and Committer before the next change is started, because a commit made from a tree holding several changes cannot be reviewed, reverted or traced back to its finding on its own.

- Never accumulate several changes in the working tree and split them into commits afterwards, whether by file or by hunk.
- A change's Pattern Sweep is its own commit, made immediately after that change's fix commit and before the next change starts. The one exception is Phase A's post-convergence sweeps, which have no fix commit of their own; each is still its own change, committed before the next.
- Pushes may be batched: Committer may push once after a run of consecutive commits instead of after each one, but the branch is always pushed before PR Submitter or CI Monitor runs.
- Run one Pattern Sweep, and make one sweep commit, per construct, not per finding or per occurrence: when several findings report the same construct at different sites, one sweep covers them all. Skip the sweep if a commit already in this PR carries a `Construct:` line for the same construct and no later commit reintroduced it; a site a later review round deliberately reverted is not reintroduced.
- If a sweep finds nothing, the fix commit body carries the `Construct:` line and `Swept: none`; no sweep commit or extra comment is needed.
- Apply a Pattern Sweep in full whatever its size; never stop, add `Blocked` or defer it to a follow-up issue because of its size.
- A Pattern Sweep hit that the build-time static analyzer stack already enforces differently is left as-is.
- A Phase A sweep that finds no hits has no fix commit of its own, so it is recorded in Phase A's status comment on the PR instead.

- In an interactive session, after each push the loop makes, hand CI to CI Monitor, stating the run mode and the phase and step to resume at, and pause the loop until CI Monitor returns, because nothing else would watch that run or return control to the loop. CI Monitor's all-pass rule then decides whether the loop resumes there or restarts at Phase A.
- An unattended run carries on within the loop without waiting, because the PR stays in draft with auto-merge off until Phase E, and Code Fixer and CI Debugger turn auto-merge off and convert to draft before any later fix, so GitHub cannot merge a fix the loop has not reviewed.

## Phase A: Simplify (up to `MAX_SIMPLIFY_ITERATIONS` rounds, with a separate `SIMPLIFY_THRASH_LIMIT`)

1. Update the workflow board to **AI Simplify**, if one is configured (see [Updating a Workflow Board](#updating-a-workflow-board) below).
2. Have Code Fixer run `/simplify` against the diff and keep its edits. `/simplify` applies reuse, simplification, efficiency, and altitude cleanups directly rather than just reporting them, so it has to run in the role that edits files, not in the Orchestrator. Code Fixer also applies IDE MCP code analysis to the modified files: best-effort use of any MCP IDE integration that is configured and connected for the files' language, additive to the language's own build and analyzer checks. It is not blocking: if none is configured or it fails to connect, skip the check for that step, comment on the PR naming the tool and why it was unavailable, and never add `Blocked` for this alone.
3. If the simplify pass changed any files: send the edits through the rest of the fix route, then return to step 2 to re-run against the resulting diff.
4. Once the simplify pass makes no further changes: have Code Fixer run a Pattern Sweep for each construct in the net Phase A diff (the commits since step 1), not per round, since rounds may revert each other and each sweep would widen the next round's diff. A change with no repeatable construct (a local rename or restructuring) has nothing to sweep. If the sweep changed files: send each construct's sweep through the fix route on its own as in step 3, one at a time, then proceed to Phase B instead of returning to step 2 (Phase B re-covers the swept code).
5. Simplify has its own iteration budget, kept deliberately separate from Phases B-D's budgets, because it is expected to run more rounds and give up without blocking:
   - Track each round's diff size (lines changed by that round's simplify commit) against the previous round's.
   - Once `SIMPLIFY_THRASH_LIMIT` rounds have run, if the current round is thrashing (its diff is flat or larger than the previous round's, i.e. not shrinking): give up immediately, even though `MAX_SIMPLIFY_ITERATIONS` has not been reached.
   - Otherwise, keep re-running up to `MAX_SIMPLIFY_ITERATIONS` rounds total; once that hard cap is reached without converging to no changes, give up regardless of whether the diff was still shrinking.
   - Either way, giving up means: post a PR comment noting that simplify did not converge, run step 4 in full (the sweeps and each sweep's trip through the fix route) on the diff as it currently stands, then proceed to Phase B. **Do not add `Blocked` and do not stop**: non-convergence in Phase A never blocks the PR, because Phase B's code-review pass re-covers the same reuse/simplification/efficiency categories as a safety net.

## Phase B: Code Review (up to `MAX_CODE_REVIEW_ITERATIONS` rounds)

1. Update the workflow board to **AI Review**, if configured.
2. Run `/code-review --comment`. This intentionally re-covers the reuse/simplification/efficiency categories Phase A's `/simplify` already applied (`/simplify` fixes them silently; this step verifies nothing was missed) and separately checks correctness, which `/simplify` does not. Security and compliance are not covered here; they remain Phase C's job. Also apply IDE MCP code analysis to the modified files. Expect this step to usually find nothing in the categories Phase A already handled.
3. If no findings were posted: proceed to Phase C.
4. Otherwise, judge convergence from the PR's history of prior code-review comments: are this round's findings substantively new/distinct, or substantially a repeat of findings already reported (and left unresolved, or fixed and now recurring) in an earlier round? `MIN_REVIEW_CONVERGENCE_ROUNDS` must be set below `MAX_CODE_REVIEW_ITERATIONS`, otherwise the round-cap branch below always fires first and the non-blocking exit can never trigger.
   - If `MAX_CODE_REVIEW_ITERATIONS` rounds have already run and findings remain, whether or not this round's findings are themselves new: post a PR comment listing the unresolved findings, add the `Blocked` label (see [Adding `Blocked`](#adding-blocked) below), and **stop**.
   - Otherwise, if substantially repeating a prior round (not converging) AND at least `MIN_REVIEW_CONVERGENCE_ROUNDS` rounds have now run: post a PR comment summarising the unresolved findings and stating that code review is not converging, advance the board to **AI Security Review** if configured, post a one-line status comment, then proceed to Phase C. **Do not add `Blocked`**: this means no new correctness issues are surfacing, not that a known one is safe to ignore; the posted comment carries the unresolved findings forward to human review.
   - Otherwise (substantively new findings, or a repeat but fewer than `MIN_REVIEW_CONVERGENCE_ROUNDS` rounds have run so far, so one failed fix attempt is not yet enough evidence to give up, and the round cap has not been reached): hand the findings to Code Fixer through the fix route one construct at a time: each construct's fix and its Pattern Sweep are committed before the next construct is handed over, and findings that report the same construct are one change (a finding that only re-reports the swept construct in files a sweep touched is not substantively new for the convergence judgment above; a new bug in those files is). Once the route has pushed the last construct, return to step 2.

## Adding `Blocked`

Wherever this loop says to add `Blocked`, post the explanatory comment and add the label with one command, `cfwf pr block --repo <owner/repo> --pr <number> --body-file <file|->`, which posts the comment, then adds `Blocked`, leaving the board as it is. Then stop as the step says.

Before adding `Blocked` for a build, SDK, analyzer, hook or other tooling problem, search the knowledge base for a recorded fix and list every search made (the error text, project type or setting searched for) in the block comment, because a fix recorded elsewhere may already apply and the human needs to see it was looked for. Use `Blocked` only when no recorded fix applies; a genuine design question still blocks as before.

## Conflict Resolution: Simplify/Code Review vs. Static Analyzer

If a change proposed by `/simplify` (Phase A) or a finding raised by `/code-review` (Phase B) would conflict with a rule enforced by the project's build-time static analyzer stack (Roslynator, SonarAnalyzer, Meziantou, Threading, Security Code Scan, and others) or by `FunFair.CodeAnalysis`, **the static analyzer's rule always wins**: do not apply the conflicting simplify/code-review suggestion, and keep the analyzer-compliant code as-is.

## Phase C: Security Review (up to `MAX_SECURITY_REVIEW_ITERATIONS` rounds)

This phase mirrors Phase B exactly, substituting security-review for code-review; keep both in sync when editing either.

1. Update the workflow board to **AI Security Review**, if configured.
2. Run `/security-review`. Also apply IDE MCP code analysis to the modified files.
3. If no findings are reported: proceed to Phase D.
4. Otherwise, judge convergence from the PR's history of prior security-review comments, the same way as Phase B step 4 above (`MIN_REVIEW_CONVERGENCE_ROUNDS` must again be set below `MAX_SECURITY_REVIEW_ITERATIONS`):
   - If `MAX_SECURITY_REVIEW_ITERATIONS` rounds have already run and findings remain, whether or not this round's findings are themselves new: post a PR comment listing the unresolved findings, add the `Blocked` label, and **stop**.
   - Otherwise, if substantially repeating a prior round AND at least `MIN_REVIEW_CONVERGENCE_ROUNDS` rounds have now run: post a PR comment summarising the unresolved findings and stating that security review is not converging, advance the board to **AI Coverage** if configured, post a one-line status comment, then proceed to Phase D. **Do not add `Blocked`**, for the same reason as Phase B's equivalent exit.
   - Otherwise (substantively new, or a repeat but fewer than `MIN_REVIEW_CONVERGENCE_ROUNDS` rounds have run so far, and the round cap has not been reached): post findings as a PR comment if not already inline, then hand the findings to Code Fixer through the fix route one construct at a time: each construct's fix and its Pattern Sweep are committed before the next construct is handed over, and findings that report the same construct are one change (a finding that only re-reports the swept construct in files a sweep touched is not substantively new for the convergence judgment above; a new bug in those files is). Once the route has pushed the last construct, return to step 2.

## Phase D: AI Coverage (up to `MAX_COVERAGE_ITERATIONS` rounds)

This phase is a whole-repo ratchet: each orchestrated language's overall line-coverage percentage on the PR branch must be at least that language's percentage on `main`, compared against a baseline committed to `main` itself (no external coverage service). It gates on the whole repo's per-language coverage, not just the lines the PR's own diff touches; it exists to catch a deleted test or a refactor that drops coverage of code the diff never touched, which the diff-coverage check done by Code Tester would miss.

1. Update the workflow board to **AI Coverage**, if configured.
2. Run the coverage ratchet decision procedure:
   1. If every file changed on the branch (relative to its merge-base with `main`) falls into a non-code category (dependency-manifest/version-pin bumps, CI workflow YAML beyond version pins, SQL, shell scripts, Dockerfiles and Docker Compose files, or documentation-only changes), skip without measuring anything and without reading or writing `COVERAGE.md`, because nothing that changed could have moved any language's coverage: post the one-line status comment `Non-code change: coverage ratchet skipped`, move the board to **Human Review**, and stop. Do not go to step 5.
   2. Fetch `origin/main` fresh (always; do not rely on a fetch from earlier in the session) and read its committed coverage-baseline file, `COVERAGE.md` at the repo root, without checking it out (`git show origin/main:COVERAGE.md`). If it does not exist yet, this is a first-time bootstrap: there is no baseline to compare against, so treat the gate as passed and continue to step 5.
   3. Have Code Tester measure: for each orchestrated language with a real baseline figure in that file (not `n/a` or `excluded`), it measures that language's current overall line coverage on the branch's working tree (already checked out), with the build MCP `coverage` tool over every component (`project: all` on `build-dotnet` for .NET, `package: all` on `build-node` for Node), producing both the per-component rows and the Overall figure, and reports them back (see [Measuring Coverage and the Baseline File](#measuring-coverage-and-the-baseline-file) below). Each successful `coverage` run writes its language's section of `COVERAGE.md` itself, and Code Tester leaves the file uncommitted. The measurement has to run in Code Tester, not in the Orchestrator, because the Orchestrator's session is not granted the build MCP tools and the raw coverage commands are denied. The Orchestrator never runs a build, test or coverage command itself; it only compares the reported figures and decides. If any test failed, Code Tester reports the measurement as void, with the failing tests, instead of figures; the Orchestrator then treats it as a Development-phase fix, moves the board back to **Development** and stops, without going to step 4. A void measurement is not a coverage-gap round and does not count towards the step 6 round cap.
   4. Compare branch vs. baseline **overall** coverage per language (never blended across languages, and never gated on a single project/component dipping while its language's overall holds or improves; component rows are recorded but never gate): any language whose branch overall is below its baseline overall fails the gate, and Code Tester then runs `git -C <repodir> restore COVERAGE.md`, so the branch keeps `main`'s baseline rather than the figures the failed round wrote.
   5. **On success**: commit the `COVERAGE.md` the `coverage` tool wrote in step 3 (in the bootstrap case, have Code Tester measure as in step 3 first, which writes it). Never write or edit the tool-written sections by hand, with a shell command, or with an edit or write tool; only a Python section, which no tool writes, is updated by Code Writer (docs only) with the figures just measured. Send the change through the fix route without Code Tester or Changelog (correction), starting at Committer when no Python section changed, resuming at Phase E, because the Orchestrator never measures, edits or commits itself, the coverage was measured moments ago, and a coverage figure is not a change the changelog records. Never commit `COVERAGE.md` from a void measurement. Move the board to **Human Review**, post a one-line status comment (`Coverage ratchet passed - advancing to Human Review`), and stop; do not let the board re-enter AI Coverage on the resulting CI run, because the phase has already advanced past it.
   6. **On failure**, check the round cap first, then judge the round-over-round trend:
      - **Round cap**: if `MAX_COVERAGE_ITERATIONS` rounds have already run (counted from prior `... - returning to Development` coverage comments) without the branch catching up, whether or not this round's trend is itself closing: post a PR comment listing the still-failing languages and their gap, add the `Blocked` label, and stop. Do not commit `COVERAGE.md`.
      - Otherwise, compare each still-failing language's overall this round against its overall in the most recent prior coverage comment that mentions that language by name (not necessarily the immediately preceding round, since a language that passed in a round leaves no comment mentioning it for that round, so a later failure must be compared against its last-mentioned figure, not a stale or absent one). Treat a language as trending, with nothing yet to compare, only when no prior comment mentions it at all, regardless of which round this is, or when this is the whole PR's first coverage round.
      - **Gap closing** (every still-failing language's overall either improved versus its own previous coverage round, or is trending per the carve-out above): post a status comment in the form `<lang> <branch-pct>% < main <baseline-pct>% - returning to Development` (one line per failing language), move the board back to **Development**, and stop. Do not commit `COVERAGE.md`.
      - **Flat or worsening, and judged unlikely to close**: post a PR comment giving the per-language numbers, the round-over-round trend, and the specific reasoning for why coverage cannot realistically be raised further here, add the `Blocked` label, and stop. Do not commit `COVERAGE.md`. Unlike Phase B/C's self-detected non-convergence exit, this one blocks: a coverage round's pass/fail IS the ratchet's own verdict, so giving up here means proposing to waive the gate itself, not merely reporting that no new findings turned up; a human must see and agree with the reasoning before the gate is treated as satisfied.
      - **Flat or worsening, but more rounds are still judged worth trying**: post the status comment as in the gap-closing case above, move the board back to **Development**, and stop. Do not commit `COVERAGE.md`.

### Measuring Coverage and the Baseline File

A coverage measurement is valid only when the test run that produced it exited 0 with every test passing. If any test fails, the measurement is void: do not read the coverage output (even when the runner still wrote a report), do not commit `COVERAGE.md` from it, and do not pass the ratchet on it. The failing test must be fixed in the same PR before coverage is measured again, whether or not it also fails on `main`. No instruction file, global or repo-local, may record a "known failure" or "pre-existing failure" exception that lets the ratchet pass with failing tests; a role that finds such an exception must report it to the instruction file's owner, not follow it.

`COVERAGE.md` is generated, never hand-edited, and is the sole persisted record of coverage. The build MCP `coverage` tool writes it, and it is committed only by this phase and by the bootstrap and rebase-conflict rules below. Every successful `coverage` run rewrites the file, including a run made outside this phase (for example Code Tester's diff-coverage check): undo that with `git -C <repodir> restore COVERAGE.md` and never commit it. Its absence is a signal, not a free pass: anyone changing a repo without a `COVERAGE.md` must create it (bootstrap) and thereafter keep it updated. The comparison is per language, never blended into one figure. A language with no code or tests present in the repo is skipped, and Shell is excluded entirely: never measure it, always record it as `excluded`, and never include it in the comparison.

- **.NET**: components are assemblies (one row per `<AssemblyName>.Tests` project's target assembly). Run the `build-dotnet` MCP server's `coverage` tool with `project: all`, and measure only unit test projects (`<AssemblyName>.Tests`), never `<AssemblyName>.Integration.Tests` or `<AssemblyName>.Benchmark.Tests`. The tool starts a job and returns its id at once: wait for it with `job_result`, calling it again only while its `state` is `running`, never by polling `job_status` and never with a shell wait or `sleep`, and wait for every job started to finish before handing back. A successful run writes the .NET section of `COVERAGE.md` itself, and its `job_result` gives the per-assembly figures for the component rows and the gated Overall (.NET) figure. The raw coverage commands are denied in the agent container, so if the `coverage` tool is not available, never measure another way: if the server is not connected, stop, comment on the issue or PR that the build-dotnet MCP server is not connected and add `Blocked`; if it is connected but does not list the tool, the repository has nothing for it to run, so say so in your report instead of composing a command. Skip .NET if the repo has no `*.Tests` project.
- **Node**: Vitest with the `@vitest/coverage-v8` provider. Run the `build-node` MCP server's `coverage` tool with `package: all`. It runs each package's `test:coverage` script and reads the Cobertura report the script writes (`coverage/cobertura-coverage.xml` by default), so the Vitest configuration must enable the `cobertura` reporter, configured alongside the `json-summary` reporter and whatever other reporters the repo already uses. A successful run writes the Node section of `COVERAGE.md` itself, and its `job_result` gives the per-package figures and the gated Overall (Node) figure. When the `build-node` server is not connected or does not list a `coverage` tool, run `npx vitest run --coverage`, then read `jq '.total.lines.pct' coverage/coverage-summary.json`, and report the figures; the Node section of `COVERAGE.md` then keeps its committed figures, because only the tool writes it. If the repository's `package.json` defines a `test:coverage` script, that script takes precedence over the Vitest default: run `npm ci` and then `npm run test:coverage` from the repository root with no arguments, `--prefix`, `cd` or redirects, and read `coverage/coverage-summary.json`. Components are packages (one row per `package.json` with a configured test runner in a monorepo layout). Skip Node if the repo has no `package.json` with a configured test runner. Adding these packages to a repo for the first time still needs the normal human approval for third-party packages.
- **Python**: `coverage.py` run via `pytest`: `coverage run -m pytest`, then `coverage report --format=total` (prints only the overall percentage). Components are packages. No `coverage` tool writes the Python section, so Code Writer (docs only) writes it. Skip Python if the repo has no Python test suite.
- **Whole-repo test-infrastructure exclusion**: when every production assembly/package for a language in the repo carries a blanket coverage-instrumentation exclusion (the repo exists solely to provide test-support libraries), record that language as `excluded` with a one-line rationale and never measure or compare it. If only some assemblies/packages carry the exclusion, measure normally.

File format: a `# Coverage` heading and the line `Generated by the AI Coverage phase. Do not edit by hand.`, then a section per orchestrated language (.NET, Node, Python, Shell), even when skipped. A measured language lists every component in a table plus a bold **Overall (\<Language\>)** row, which is the figure the gate compares; a language with one component still gets an explicit Overall row. A .NET or Node table has four columns: the component name, `Line Coverage`, then the `Covered` and `Coverable` line counts; the Overall row's counts are the sums of the component rows' counts, its percentage is calculated from them, and the gate reads only its `Line Coverage` percentage, which stays the second column. A component row reading `n/a` counts as 0 covered of 0 coverable lines. Python's table has the two columns `Package | Line Coverage`. A `coverage` run of every project or package writes its language's whole section and the commit line, and leaves every other section as it is. Use `n/a (no code)` for a language with no code or tests (no table), and `excluded` for Shell or a whole-repo test-infrastructure exclusion (with a one-line rationale in the latter case). End with a `---` line and the line `Captured at commit <sha> on <ISO-8601 date>.`, where `<sha>` is the commit the numbers were measured against. The file records only the coverage figures (the component rows, the Overall rows and the `<sha>` line): it must never record the command, tools, flags or runner used to measure them, because later rounds would copy that recorded command instead of following the repository's own coverage instructions, so remove any such line when updating the file.

Conflict on rebase: `COVERAGE.md` is generated content, never text-merge conflicting percentages. If a rebase onto `origin/main` produces a conflict in `COVERAGE.md`, take `main`'s copy (`git -C <repodir> checkout --ours -- COVERAGE.md`, then `git -C <repodir> add COVERAGE.md`; during a rebase `--ours` is the branch being rebased onto, the opposite of a merge) and continue the rebase as normal. Once it completes and the post-rebase build-and-test step passes, re-run the per-language measurement against the rebased working tree and commit the fresh `COVERAGE.md` as part of that same rebase work; do not leave `main`'s stale copy in place, and do not measure before the build and tests are confirmed green.

Bootstrap: `COVERAGE.md` reaches `main` for the first time via whichever branch's Pre-Work Baseline Check first finds it missing, as that branch's own first commit. Because `origin/main` still lacks the file, the comparison finds nothing to compare against on that same branch and must not block; measure the branch as above, which rewrites `COVERAGE.md` with the branch's live figures, and commit it (its second commit on that branch, which is expected), treat the gate as passed, and proceed as in the success case.

## Phase E: Mark Ready

Only once all four phases have completed without a `Blocked` outcome (each phase passed outright, or exited via its own non-blocking convergence path noted in a PR comment, or there were no reviewable changes):

- **P1.** Safety net (belt-and-suspenders on top of the Code Reviewer role's own Compliance sub-agent check): confirm a `.deleteme.now` placeholder file is not present in `git -C <dir> diff origin/main...HEAD --name-only`; if it is still present, have Code Writer remove it and send it through the fix route without Changelog (correction), with Committer giving it its own commit, because a template-skip item has no changelog entry to correct, then continue.
- **P2.** Hand the PR off to human review in one command. Give the PR's final title (Conventional Commits) and its final description (what the change does and why, replacing whatever the description says now, such as the placeholder it was opened with) in one command, with the description on stdin. Write no file first and chain nothing around it:

  ```bash
  cfwf pr hand-off --repo <owner/repo> --pr <number> --title "<type>(<scope>): <description>" \
    --description-file - <<'DESCRIPTION'
  <what the change does and why; keep every Closes #N line, including those for completed sub-issues>
  DESCRIPTION
  ```

  `--body-file <file>` is optional, for extra review-record text. Without it, the record is `cfwf`'s own first line naming the head it reviewed, which is enough.

  It checks everything before it writes anything, then, always in this order: sets the title and description, moves the board to **Human Review** (whether or not Phase D already did), marks the PR ready, posts the review record, and enables auto-merge. Never run those steps separately or with a hand-written comment, because the order is what keeps unreviewed or un-checked change from merging. Judge it by its exit code:

  - **0**: handed off, with auto-merge on, or unavailable on the repository (then the PR is left ready for a human to merge, which it says).
  - **7**: ready and recorded, but auto-merge deferred, because the checks that start once the PR is marked ready have not all finished, or one failed. GitHub counts a check skipped on a draft as passed, so enabling auto-merge straight after marking ready could merge before lint, secret scanning and dependency review have run; `cfwf` enables it only once every judged check whose latest result on the current head before the PR was last marked ready was a skip, or which had no result then, has a result completed at or after that time. A judged check whose pre-ready result on the same head SHA is a genuine pass (success, not skipped) already counts as passed and needs no post-ready result, and one whose pre-ready result is a failure still counts as failed. See P3.
  - **8**: refused, nothing written. Read the rule from `cfwf: hand-off refused: <rule>` (or `cfwf: body refused: <rule>`) on stderr: a title that is not Conventional Commits, a leak or a plan-approval keyword in the text, a PR that is not open or carries `Blocked` or `On Hold`, or required checks that failed, are pending or have not reported at all. Fix what is yours to fix (the title or text) and run it again; for failing checks follow [Reading CI Check State](#reading-ci-check-state) below; otherwise stop and report.
  - **9**: the PR does not exist. **1**: a runtime failure (API or network) naming the steps already done; retry later. **2**: a usage error.

  The review record is the comment `### AI Review Loop: reviewed <full head SHA>`, followed by the text from `--body-file`. `cfwf` writes that first line itself, from the head it read at the start, so the SHA can never be mistyped or stale, and it posts the record on every run, even when the PR was already ready, because this comment is the record of which head the loop last reviewed, and neither the PR's draft state nor its `ready_for_review` events move forward when the loop re-runs on a PR that is already ready.

  The PR has an unreviewed commit when its head SHA (`cfwf pr view --repo <owner/repo> --pr <number> --field head-sha`) differs from the SHA in the latest accepted `### AI Review Loop: reviewed` comment, or when there is no such comment, because unreviewed change must not merge. Accept such a comment only when its author login is the bot login the orchestrator passes in, or a trusted commenter (a login in the "Trusted commenters" list the orchestrator passes in, or only the repository owner's login if no list is provided), because anyone else could post one naming a head the loop never reviewed. The bot login counts here, unlike when judging approvals, because `cfwf pr hand-off` posts this comment from it. When no bot login is passed in, use the authenticated login that `cfwf auth status` prints as the bot login for this check only, because otherwise no record is ever accepted when the repository owner is an organisation (no login is then trusted), so every run would see an unreviewed commit and rerun the whole loop. A rebase leaves an unreviewed commit and re-runs the loop, except in the rebase carry-forward case below, because re-reviewing is safe while wrongly skipping review is not.

  **Rebase carry-forward.** After a rebase, re-run the loop only when the rebase changed the PR's own code or needed conflict resolution. Compare the PR's own changes before and after, with `git range-diff <old-base>..<old-head> <new-base>..<new-head>` or by comparing `git diff <merge-base>..<head>` for the PR's files. When the diff is unchanged and the rebase was conflict-free, treat the rebased head as reviewed: post a new `### AI Review Loop: reviewed <new head SHA>` comment that says it carries the earlier review forward, naming the old SHA and why, then continue to Phase E. Required CI must still pass on the new head. When the diff changed or conflicts were resolved, the head is unreviewed and the loop runs again from Phase A. Only the bot login or a trusted commenter may post the carry-forward comment, as for any `reviewed` comment.

  Phase E is the only step that takes a PR out of draft, because every other role leaves it as draft until the loop has reviewed every commit.
- **P3.** When the hand-off exits **7** (deferred):
  - In an interactive session, hand CI to CI Monitor, stating the run mode and that the required checks skipped while the PR was a draft are now running for the first time, because those checks have never run and nothing else would wait for them. CI Monitor handles any failure as a CI failure. When CI Monitor returns control after confirming all required checks pass, run the same `cfwf pr hand-off` again.
  - In an unattended run, stop here, because `oneshot` re-invokes the agent when the checks change. On a later invocation, when the PR is open and not a draft, `cfwf pr view --repo <owner/repo> --pr <number> --field auto-merge` prints `off`, the PR has no unreviewed commit and [Reading CI Check State](#reading-ci-check-state) confirms all required checks passed, run the same `cfwf pr hand-off` again, because that combination is what a PR waiting at this step looks like. It exits 7 again while a required check that needs a post-ready result (one whose latest pre-ready result on the current head was a skip, or which had none, as exit 7 above describes) has none yet; leave the PR as it is then.
  - If the PR has an unreviewed commit, for example from a Rebase Agent or human push, first take it back with `cfwf pr take-back --repo <owner/repo> --pr <number> --body-file <file|->` (a body saying why), which turns auto-merge off first, then converts the PR to draft, moves the board to **Development** and posts the body as a comment; never do those steps separately, because converting to draft alone does not turn auto-merge off. Then run this loop for it instead of handing it off again, because unreviewed change must not merge, and a draft PR is what lets the loop's own Phase E mark it ready again and start the post-ready checks.

Before closing any issue or PR, including at this phase's closing points, check whether its Implementation Plan (Approach or Files-to-change text, or an Open Question) or a later comment on it flagged a specific decision as required or pending (for example "needs policy sign-off", "pending a decision on X", an unresolved `Qn.`). If so, do not close until that specific item has a visible resolution of its own (a comment recording the decision, a link to the resolving issue or PR, or an explicit retraction), not just implicitly overtaken by whichever branch of the plan got implemented. Removal of `Blocked` is not itself sufficient evidence that this check is satisfied.

## Reading CI Check State

Check the state of the required checks once, because the PR is mergeable without the optional ones:

```bash
cfwf pr checks --repo <owner/repo> --pr <number>
```

It reads the required checks of the PR's base branch from its protection and rulesets (every check when the branch requires none), judges the newest run of each on the PR's current head, and never waits. Judge the result by its exit code, never its printed text:

- **0**: every required check passed (skipped and neutral count as passed).
- **3**: at least one required check failed; a cancelled, timed-out or stale one counts as failed, because GitHub treats it as unsatisfied and the PR cannot merge until it runs again.
- **4**: none failed and at least one is pending, including a required check with no result yet.
- **5**: the head has no check runs or statuses at all. That is not a pass; treat it as pending.
- **1**: an API or network error, never a failed check. **2**: a usage error.

Then act immediately; do not wait for the checks to settle yourself, in any mode, because a blocking wait holds the session for the whole CI run. Only CI Monitor waits for checks, in the background.

Accept an all-passed result only if it is still true on the next check after it was first seen, because a fast required workflow can pass before a slower one has even been queued. In an unattended run, the `oneshot` gate's check before invoking the agent is the first sighting, so this check confirms it; in an interactive session this check is the first sighting, so hand the PR to CI Monitor, stating that the session is interactive, because its `cfwf pr checks-wait` run confirms the pass on two reads of its own. If a required check is pending or in progress, or none has reported yet, and none has failed: in an unattended run, stop silently without posting a status comment, because `oneshot` re-invokes the agent once the checks settle; in an interactive session, hand the PR to CI Monitor instead of stopping, stating that the session is interactive. Route a failed required check to CI Debugger rather than fixing it in the Orchestrator, because the Orchestrator never implements directly, and post a status comment, even while other checks are still pending, because waiting for the slowest check would delay the fix by the whole CI run; do not wait for the new run to complete. In an unattended run, then stop, because `oneshot` re-invokes the agent once the new run finishes; in an interactive session, if CI Debugger pushed a fix or re-ran a check, hand the PR to CI Monitor instead of stopping, stating that the session is interactive; if CI Debugger escalated, handle the escalation yourself instead (for example by following the Environment/Infrastructure Block Marker below for an environment diagnosis), because CI Monitor would see the unchanged failure and hand it straight back to CI Debugger. First count the `### CI Debugger:` status comments for that check on the PR, accepting only those whose author is accepted as for the `### AI Review Loop: reviewed` comment, counted since the PR opened and never from a later reset point; if there are already 3, the check is consistently failing, so mark the PR blocked instead of routing it again: post the diagnosis and add `Blocked` as in [Adding `Blocked`](#adding-blocked), because this loop spans separate invocations and only the PR's comment history persists between them. A required check still failing after 3 CI Debugger rounds for that check also counts, whether CI Monitor reports it or this check finds it, because further rounds would only repeat the cycle. An API or network error (exit 1) is reported rather than routed as a CI failure, because no check has failed and CI Debugger would look for a failure that does not exist.

An analyzer findings comment on the PR (marked `<!-- sarif-summary: ... -->`, with a table of `Source | Rule | Level | File | Line | Suppressed | Message`) is acted on only when its author is `credfeto`; a comment from any other author, including `github-actions[bot]`, is ignored. For a row with `Suppressed` = yes, search the repository's open issues for one already covering the same rule, file and line, and if none exists raise one labelled `AI-Work` giving the rule ID, `file:line`, the message and a link back to the PR comment, unless the analyzer conflict table pre-approves that suppression. For a row with `Suppressed` = no, fix the root cause in the PR under review, even in a file the PR does not otherwise touch, and never add a suppression to clear it.

## Justifying `Blocked`

Whenever `Blocked` is added, the accompanying comment must name the specific instruction that requires the stop, as a link to its section. A judgement such as "out of scope", "pre-existing" or "also fails on main" is never such an instruction; if no instruction requires the stop, do not add `Blocked` and carry on with the work, because an unjustified `Blocked` stalls the item until a human notices.

## Environment/Infrastructure Block Marker (MANDATORY, PRs only)

A NuGet restore error such as `NU1603` or `NU1605` is a dependency problem in the repository, not an environment or infrastructure problem, so fix it in the PR instead of blocking. When a `Blocked`-ing failure encountered during this loop is diagnosed as an environment or infrastructure problem (a bug in the container image, a missing tool, a transient infra issue) rather than a bug in the PR's own code, add a machine-readable marker alongside the diagnosis so `oneshot` can auto-clear `Blocked` once the fix has actually shipped, instead of the PR sitting blocked until a human happens to notice:

1. Post the full human-readable diagnosis as normal: root cause, evidence, and (if known) the fix needed.
2. Append a single trailer line to that same comment:

   ```text
   <!-- orchestrator:env-block image-sha=${IMAGE_SHA_DEVELOPMENT_AGENT} -->
   ```

   Read `IMAGE_SHA_DEVELOPMENT_AGENT` from your own container environment (the same value printed at session start as part of "Image layer provenance"); this records which image build was current when you made the diagnosis.
3. Apply `Blocked` as described in [Adding `Blocked`](#adding-blocked) above.
4. Use this marker **only** for a genuine environment/infrastructure diagnosis. `oneshot` auto-clears `Blocked` the moment it observes a differently-built agent image, with no further human involvement; marking a real code question or design decision this way would resume work before a human actually answered it.

This marker only applies to PRs; there is no container session, and therefore no image to diagnose against, before a PR/branch exists.

## Updating a Workflow Board

Always use `cfwf` for the Workflow board; never hand-compose board queries or mutations. Every command names the item as `--repo <owner/repo>` plus `--pr <number>` or `--issue <number>`:

```bash
# Move the PR to a status (matched by display name, case-insensitive)
cfwf workflow-status --set --repo <owner/repo> --pr <number> --status "AI Review"

# Read the current status
cfwf workflow-status --check --repo <owner/repo> --pr <number>
```

- `--set` adds the item to the board if it is not already there and sets the status, then prints confirmation; exit 0 means the write was accepted (do not re-read it to confirm; GitHub's state lags behind writes). A non-zero exit means the write failed.
- `--check` prints the current status and exits non-zero if the item is not on the board. The output starts with the status name: match the name exactly and ignore anything after it.

Always attempt `cfwf` rather than deciding in advance that no board is configured: only conclude there is no board if `cfwf` itself reports finding no "Workflow" project linked to the repo, in which case skip board updates silently for the rest of the session.
